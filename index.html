Segstream Design System

Rebuilding a design system so that everything themeable lives in variables — one token edit moves the entire product, with no manual cleanup.

Role
Lead UI/UX Designer
Version
v2.0, Sep 2026
Scale
40 sets · 485 variants
Impact
Retheme in 5 edits

Overview

Segstream's design system, rebuilt so that every colour, size, radius and typeface lives in a variable. Version 2.0 ships 40 component sets at 485 variants, 416 variables across seven collections, 23 text styles and a local 54-glyph icon set, with two colour modes and three density modes throughout. The organising promise is simple: one token edit moves the entire product — every component, every screen, both modes — with no manual cleanup afterwards.

The Challenge

The original file had 19 component sets and 245 variables, and it had drifted. Colour was bound directly to primitives in places, so a brand change meant hunting through components rather than editing a ramp. Dark mode existed in name only. There was no icon set, and the documentation was built from raw hex values that quietly disagreed with the components they described. Rethemeing was manual work with no way to know when it was finished.

The Solution

A three-tier token architecture, held together by one rule: a component never binds to a primitive. Raw hex lives in a hidden primitives collection. A semantic layer — background, foreground, border, brand, status, shadow — carries both modes and aliases those primitives. Component tokens alias the semantic and layout tiers in turn. On top of that structure, an entire retheme collapses to five edits: the brand ramp, an optional neutral ramp, two font families, three radius values, and a single logo component.

Design Process

1

Audit what was there

  • Catalogued the existing file: 19 component sets, 245 variables, and documentation generated from raw hex rather than from the tokens themselves
  • Traced where colour bound straight to primitives, which is what made rethemeing a manual hunt
  • Established that dark mode was present in name only, and that there was no icon set to speak of
2

Rebuild the token foundation

  • Seven variable collections arranged in three tiers, each with scopes and descriptions, and primitives hidden from publishing so they cannot be bound by accident
  • A semantic colour layer carrying genuine light and dark modes, verifiable side by side on the Colors page before a single screen is touched
  • Layout tokens with Compact, Default and Spacious density modes, and a typography collection with separate desktop and mobile scales
3

Rebuild the component library

  • 40 component sets at 485 variants, each page following the same shape so reading one teaches you how to navigate the rest
  • A shared property vocabulary — Variant, Type, State, Checked, Size, Mode — so the same word means the same thing on every component instead of being reinvented per family
  • A local 54-glyph icon set drawn on a 24px grid, with every fill bound to a token so an icon inside a button inherits that button's foreground colour
  • Building blocks prefixed with a dot to keep them out of the asset panel while still composing the larger components
4

Document it so it holds

  • Foundations pages render from live variables — the swatches on screen are the tokens, so documentation cannot drift from the system
  • Patterns and Templates built only from instances, demonstrating how components combine without introducing new one-off drawings
  • Every component page lints at zero across all eight checks, making "no raw values" an enforced property rather than a stated intention

Key Learnings

  • If something cannot be changed through a property, that is a gap in the component — not a reason to detach. Exposing every visible property is what keeps instances intact.
  • Composition beats redrawing. A modal footer holds real Button instances; redrawing a component inside another quietly breaks the token chain that everything else depends on.
  • An overridden font size survives happily until the scale changes, then silently disagrees with everything around it. Binding every text node to a style avoids a class of bug that is invisible until it is everywhere.
  • Density and breakpoint belong on the page frame, not on individual components. Setting them per component is how a system starts to contradict itself.
  • Documentation that renders from live tokens cannot drift. Documentation built from copied values always does.
  • State the limits in the open. Success, warning and error keep their own colour scales because Figma variables cannot compute colour — recolouring them means editing 33 more stops. Writing that down is better than letting the next person discover it halfway through a rebrand.

Linking an Insurance Policy Inside a Banking App

EastWest Bank customers hold EastWest Ageas policies they can only see by logging into a separate site. This flow brings those policies into the banking app — proving identity, capturing consent, and handling every way the link can fail.

Role
Product design — flows, states, UX writing
Platform
Mobile · EastWest Bank app
Partner
EastWest Ageas Life Insurance
Scope
9 flows · 80+ screens

Overview

Plenty of EastWest Bank customers also hold an EastWest Ageas life insurance policy — but the two lived apart. Checking a policy meant leaving the banking app, remembering a second set of credentials, and signing into an insurance site built for a different purpose. Most people simply never looked. This project brings those policies into the app customers already open daily, and designs the whole connection: who you say you are, what you agree to, and what happens when any part of it goes wrong.

The Challenge

Linking a bank account to an insurer is only partly a technical problem. It is mostly a trust problem. The flow has to prove identity convincingly enough to justify showing financial products, ask for consent in language a person can actually read, and never strand someone when a policy number is mistyped, a one-time code expires, or the insurer's system stops answering. The happy path is the short part of this work — the failures are where the experience is won or lost, and they are usually the part nobody draws.

The Solution

One clear journey — prompt, consent, policy number, one-time code, handoff — with every branch off it designed rather than left for the back end to explain. Friction is sized to consequence: linking moves quickly, unlinking stops to confirm. Failures are separated by cause, so a wrong code and an expired code say different things and offer different ways forward. Contact details are validated at the point of entry instead of failing silently later. And a customer who holds no policy meets a short introduction rather than a locked door.

Design Process

1

Map the journey end to end

  • Charted the happy path first — prompt, consent, policy number, one-time code, handoff — so the shape of the journey was settled before any state was styled
  • Numbered every step in flow order, with letters marking alternate routes branching off a step, so a reviewer can follow a path without guessing
  • Laid the work out in lanes that read left to right, each lane a phase, keeping an 80-screen flow legible on one board
2

Earn the link with identity and consent

  • Designed verification as a sequence a person can follow — account details, then a one-time code — rather than one intimidating form
  • Wrote consent in plain language, making it clear what is being connected and what the bank will be able to see
  • Sized friction to consequence: linking is quick, while unlinking pauses to confirm, because the cost of an accidental unlink falls on the customer
3

Design the failures, not just the success

  • Six edge-case sets covering one-time codes, policy numbers, contact details, account linking, and the back end itself refusing to answer
  • Separated failures by cause — a wrong code and an expired code are different problems and get different messages and different next steps
  • Replayed the entire journey against a failing API, which surfaces gaps the happy path hides
  • Gave every refusal a named reason and a route out, so no screen is a dead end
4

Turn a dead end into an introduction

  • Designed a lead-capture path for customers with no policy to link, so the flow still has somewhere to go
  • Kept it to what is genuinely needed to follow up, rather than a full application inside a banking app
  • Designed its failure states too — field rejections and submission failures — so the cross-sell path holds up as well as the primary one

Inside the Cross-Sell

The cross-sell is where linking stops being plumbing and starts earning its place: a customer with no Ageas policy meets an offer on the dashboard, agrees to share their details, and becomes a warm lead for an advisor — without filling in an insurance application inside a banking app.

Key Learnings

  • Friction should be proportional to consequence. Linking a policy can be quick; unlinking one should not be, because the person who pays for a mistaken tap is the customer.
  • Two different failures deserve two different messages. Collapsing "wrong code" and "expired code" into one generic error tells someone that something broke without telling them what to do about it.
  • Validating contact details at the point of entry prevents the worst kind of failure — the silent one, where a confirmation is sent somewhere the customer will never see it.
  • A refusal without a route out is a dead end. Naming the reason and offering the next step turns a stopped journey into a recoverable one.
  • Replaying the whole journey against a failing back end is the fastest way to find the states nobody designed.
  • Annotating a large flow in the file itself — numbered steps, lettered branches, lanes for phases — means engineering can read a path without a meeting to explain it.

Designing a Delivery App from Research to Launch

myEntrego is a customer-facing parcel app — book a delivery, pay for it, and see where it is. I owned it end to end, from user research through to the 113 screens that shipped on the App Store and Google Play.

Role
Lead UI/UX Designer — end to end
Platform
iOS & Android
Scope
113 screens · 2 personas
Outcome
4.8★, shipped to both stores

Overview

Entrego is a Philippine logistics company, and myEntrego is how its customers actually reach it — booking a delivery, paying for it, and tracking where the parcel has got to. This was mine from the first interview to the last screen: research and personas, a journey map, the information architecture, the booking flow, and 113 designed screens. It shipped to both app stores and settled at around 4.8 stars, with parcel tracking pulling the most repeat traffic.

The Challenge

Sending a parcel through a logistics provider meant phone calls, guesswork about cost, and no way to know where anything was once it left your hands. The research made the friction specific rather than general: booking took too many steps, addresses were hard to pin down, and the bill could not be read in full. The app also had to make sense to two very different people — a seller running a small business from her phone, and a courier who had spent ten years on a motorcycle and described himself as afraid of technology.

The Solution

Every significant decision traces back to something a real user said. Booking became a guided flow with saved addresses, so the second delivery is far quicker than the first. A shipping fee calculator puts the cost up front, before anyone commits. And tracking was made available without logging in at all — the thing people do most often became the thing that asks least of them, which is what turned it into the app's most returned-to screen.

Design Process

1

Research actual users, not assumed ones

  • Built two personas from gathered data rather than invention — Rica, a freelancer growing an online selling business, and Roger, a courier ten years into the job
  • Recorded frustrations in the users' own terms: a tedious booking process, trouble locating an address, and a bill that could not be seen in full
  • Kept a self-described "tech phobic but willing to learn" user in scope, which set the standard for how much each screen had to explain itself
2

Map the journey, including how it feels

  • Plotted the end-to-end journey in swimlanes — steps, actions, expectations, thoughts — and ran a feelings lane alongside them
  • Marked where people were confused or frustrated, and treated those low points as the brief rather than as commentary
  • Turned the "potential improvements" lane into the backlog the screens were designed against
3

Settle the structure before the pixels

  • Built a sitemap covering profile, saved addresses, bank accounts, the fee calculator, serviceable-area checking, pouch requests, FAQs and legal
  • Drew booking as a decision tree with explicit yes/no branches, including how saved addresses short-circuit the long path
  • Resolved the awkward questions on the flow board, where changing your mind costs nothing
4

Design it, then ship it

  • 113 screens from first-run onboarding through to payment confirmation
  • Standard delivery, drop-off, scheduling, remittances, tracking and modal states all specified rather than left implied
  • Shipped to the App Store and Google Play, where it has held around 4.8 stars

Selling Health Cover Inside a Wallet App

KwikCare plans bought without ever leaving GCash — five tiers priced from ₱995 a month, a guided four-step purchase with health declaration and document upload, and a policy dashboard for every plan.

Role
Lead Product Designer
Platform
Mobile · GCash
Underwriter
PhilCare
Scope
5 plan tiers · 4-step purchase

Overview

KwikCare is health cover sold as a monthly subscription, underwritten by PhilCare and bought inside GCash — the wallet a large share of the Philippines already has open. The work covers the whole commercial path: comparing five plan tiers, understanding what each actually covers, completing a health declaration and document upload, paying from a wallet balance, and then living with the policy afterwards.

The Challenge

Insurance is difficult to sell on a phone for two reasons. The product is hard to compare — benefit limits, exclusions and waiting periods do not fit on a card — and the purchase asks for exactly the things people abandon forms over: identity documents, proof of income, and a declaration about their own health. Doing this inside someone else's app raises the bar again: the flow has to feel like a native part of GCash, or the trust that made the wallet worth using does not carry across to the insurance sitting inside it.

The Solution

Tiers are presented as a comparison rather than a brochure: each plan leads with its price and its maximum benefit limit, then lists what it actually includes. Every tier carries its own covered-and-excluded breakdown instead of one generic table, because the differences between plans are the entire decision. The purchase is cut into four named steps so the length is visible from the start, and the health declaration is kept short and in-flow rather than deferred to a form nobody finishes.

Design Process

1

Wireframe the whole purchase before styling any of it

  • Laid out the full path — plan selection, policy holder details, documents, review, payment handoff — in low fidelity first
  • Settled the step count early, which is what determines whether the purchase feels finishable
  • Used the wireframes to expose the awkward middle of the flow, where identity and health questions land
2

Make five tiers genuinely comparable

  • Led every plan card with price and maximum benefit limit, the two numbers the decision actually turns on
  • Gave each tier its own covered, excluded and expanded-detail views rather than one shared table that hides the differences
  • Marked the popular tier explicitly, so the default choice is obvious to someone who does not want to become an expert
3

Design the parts people abandon

  • Split the purchase into four named steps — insurer details, policy holder information, document upload, review — so progress is always legible
  • Designed the health declaration as a short in-flow set of statements, with a popup for the detail rather than a wall of text inline
  • Specified document upload states properly: accepted formats, size limits, in-progress and attached, because this is where a purchase quietly dies
  • Ended on an explicit review of everything captured before any money moves
4

Iterate, then specify it for build

  • Worked through four versions, keeping the superseded ones archived rather than deleted so the reasoning stays visible
  • Built a prototype of the working design so the flow could be walked rather than described
  • Produced a specifications page for handoff, alongside FAQ, how-to-claim and contact screens that the product needs after the sale

Rebuilding a Product Listing Page

The KwikCare plan listing, rebuilt so the plans can actually be compared — price leading every card, one plan recommended, and the two states nobody designs specified at both breakpoints.

Platform
Web · desktop & mobile
Page
kwik.care plan listing
Scope
7 screens · 3 states each
Status
Design complete, not yet shipped

Overview

KwikCare sells subscription health plans online. The plan listing is the page where the decision actually happens — it is where someone works out which plan they can afford and what it covers, and it is the last page before the product detail and the enrolment flow. This is a redesign of that page at both breakpoints, including the states it enters when there is nothing to show and nothing yet loaded.

The Challenge

The live page listed plans without letting anyone compare them. Every card carried the same block of coverage copy — identical eligibility wording repeated five times — so the differences between plans, which are the entire decision, were buried in text that read the same on every row. Price sat small and right-aligned, competing with a button rather than leading the card. The filters were a column of radio buttons and checkboxes behind an Apply button, so narrowing the list cost a round trip. Nothing marked which plan most people take.

The Solution

Price leads now, at the size of a headline, because affordability is the first question and there is no reason to make anyone hunt for it. Each card carries three benefits written for that plan rather than one block of shared boilerplate, so scanning down the row surfaces difference instead of sameness. The popular plan is labelled. Filters apply live against a running count, and the budget range — six radio buttons on the old page — became a single slider. The empty and loading states are designed rather than inherited.

Design Process

1

Work out what the page is being asked

  • Treated the listing as a comparison problem rather than a catalogue problem — the visitor is choosing between plans, not browsing them
  • Identified the two numbers the decision turns on, price and maximum benefit limit, and gave them the top of every card
  • Kept the plan's provider visible on the card, since who underwrites the cover is part of whether it is trusted
2

Cut the copy that was identical on every card

  • Replaced the repeated eligibility and coverage paragraph with three checked lines written per plan
  • Let the differences do the work: the cheaper plan leads on teleconsultation, the popular one on benefit limit
  • Moved everything else behind View Details rather than pre-loading the card with detail nobody reads at this stage
3

Make filtering feel like filtering

  • Dropped the Apply button on desktop so results narrow as the filter changes, against a count that updates with them
  • Collapsed six budget brackets into one slider with the selected ceiling stated above it
  • Kept Apply on mobile, where the filters live in a bottom sheet and batching the changes is the right behaviour for the pattern
4

Design the states the page spends real time in

  • Gave the empty state a reason and a route out — it names which filters are too narrow and offers both clearing them and browsing everything
  • Built the loading state as skeleton cards shaped like the real ones, so the layout does not jump when the plans arrive
  • Left the filter panel live while loading, so the page never takes control away from the person using it

Key Learnings

  • Copy repeated identically on every card is worse than no copy at all. It costs vertical space, slows the scan, and actively hides the differences a buyer is trying to find.

  • Empty states should name the cause. "No results" is a dead end; "your budget is too narrow, here is how to widen it" is a route back into the catalogue.
  • Skeletons shaped like the real card stop the layout jumping on arrival. A spinner tells you to wait; a skeleton tells you what is coming.

A Coffee Scale That Tells You Everything Except What To Do

The Timemore Dot is a lovely little scale. Its app shows you numbers, but never tells you what to do with them. So I built the app it was missing.

Role
Designed and built it myself
Timeline
One week of evenings
Platform
Web app on iPhone
Status
Live — I use it every morning

Overview

The Timemore Dot is a coffee scale about the size of a coaster. It has no screen of its own — it sends the weight and the time to your phone instead. The hardware is genuinely nice. The app that comes with it is where it falls down: it shows you plenty of numbers, but it never helps you use them. This is the app I built to replace it.

The Challenge

Making pour-over coffee is a timed routine. You pour water up to 90 grams by 40 seconds, stop, wait, then pour up to 135 grams by 1:20. The app knows the weight. It knows the time. It never puts the two together.

So you end up keeping track yourself, while both hands are busy holding a kettle. Is it time yet? Am I there yet? Do I stop now?

It trips up two kinds of people for the same reason. If you are new, you do not know the routine, and the app cannot help because it has no idea what you are making. If you have done this for years, you know the routine but you are still doing sums mid-pour — the recipe says stop at 90, the screen says 62, so you are subtracting in your head, over and over, with wet hands.

The app tells you what is happening. What you actually need is what to do next.

The App It Replaces

This is what comes in the box, and it is worth looking at closely, because most of what is wrong with it is wrong in a quiet way.

Four things are missing, and together they are the whole reason I built something else.

  • A picture where the information should be. The biggest thing on screen is a drawing of a brewer. It looks exactly the same when the cup is empty as when it is full, so it tells you nothing — and it is sitting in the spot your eyes go to first.
  • Numbers, but no advice. Around it you get the weight, the flow rate and a timer. All of them are true. Not one of them tells you what to do.
  • No recipe anywhere in it. The app has no idea you are aiming for 90 grams at 40 seconds, so it cannot tell you that you are getting close, and it cannot tell you to stop. Nobody ever told it where you were going.
  • A timer you have to press. You start it yourself, with a full kettle in your hand, which costs you a few seconds at the exact moment you can least spare them.

The Solution

The biggest number on my screen changes depending on what you are doing.

While you are pouring, it shows how many grams you have left, counting down to zero. While you are waiting, it shows how many seconds until the next pour. The weight is still there, just smaller, for when you want to check it.

That is really the whole idea: the app does the sums so you do not have to.

Everything else follows from it. A pour finishes when the scale says you got there, not when a timer guesses. The card changes colour so you can read it from across the kitchen. Four different sounds cover the moments your eyes are on the coffee and not the phone. And the timer starts itself the moment water hits the scale, so there is nothing to press.

How I Got There

1

My first idea did not work, which turned out to be useful

  • I wanted a small floating window on top of the Timemore app — their numbers, my prompts
  • One search ended that: iPhones do not let other apps draw on top of each other. Android does; iOS does not
  • That forced a better question — if I cannot sit on top of their app, do I need their app at all? I did not. Timemore publishes how the scale talks over Bluetooth, so their app is just one way to listen
2

I checked the risky part first

  • Before designing anything, I made sure I could actually talk to the scale — tare it, start and stop the timer, reset it, change units
  • Checked my version of each command against a working one from someone else's code. All six matched
  • Twenty minutes of that removed the one thing that could have sunk the project, before I had drawn a single screen
3

I made the biggest number the useful one

  • Grams left while you pour, seconds left while you wait — the main number swaps jobs depending on what is happening
  • My first version guessed how long a pour would take and cued you off a timer. It was wrong every time I poured slowly, and every prompt after it was wrong too
  • Connecting the scale fixed that: the pour ends when you actually get there. Go over, and the card turns red and tells you by how much
4

I designed it for someone who is not looking at the screen

  • Your eyes are on the coffee and your hands are wet, so the card floods with colour the second a pour starts — you catch it out of the corner of your eye
  • Four sounds that are shaped differently rather than four versions of the same beep, so you can tell them apart without looking
  • The timer starts on the first couple of grams of water — heavy enough to ignore a knock, light enough to catch the start of a pour
5

I let people type what they are actually thinking

  • Recipes are written as running totals, but nobody thinks "this pour takes me up to 177 grams" — they think "45 grams here". So you type the amount you are adding, and the app works out the total
  • You never start from an empty form. Put in your dose and strength and it writes you a working recipe, or copy a well-known one so a James Hoffmann brew is two taps
  • It checks your maths too — if your pours do not add up, or one is scheduled to take longer than the gap before the next, it says so and offers to fix it

Inside the Work

Building It With AI

I would rather be straight about this than pretend I hand-wrote three thousand lines of Bluetooth code. I decided what it should do and how it should behave. The model wrote most of the code, and when I asked it to go looking for problems, it found a few I would otherwise have shipped.

Mine

Spotting that the app should be telling you what to do rather than what is happening. The number that swaps jobs. Letting people type amounts instead of totals. The sounds, what to throw away, and giving up on the floating window in favour of talking to the scale directly.

The model's

The Bluetooth code, reading the data off the scale, and a speed pass that cut the work the app does on every update by about 99%.

Caught by testing, not looking

The "start pouring" sound never played. The code meant to trigger it sat inside a section that stopped running the moment a pour began. Nothing looked wrong on screen — it only showed up when I ran a fake brew end to end.

The part that still takes judgement is the same as it has always been: working out which problem is worth solving, what to leave out, and when something is quietly not doing what it claims. It got faster. It did not get easier.

Taking It Out Of My Kitchen

Everything above was me, in my own kitchen, with my own recipe. So I took it to a friend who runs a cafe and handed it to two people who had never seen it before.

Falling Beaker — a small place, and two people who make coffee for other people all day. A harder test than my own kitchen at seven in the morning.

What he took from it was something I had not framed for myself. I had been thinking about it as a tool for one person making one careful cup. He saw it as a way to get the same cup out of different people — the trainees learning the routine by following it, and the experienced staff hitting the same targets they would otherwise be eyeballing. Consistency across a team, rather than help for a beginner.

That is a different product from the one I set out to build, and a bigger one. It also changes what is worth measuring: not just whether my pours get closer to target, but whether two different people pouring the same recipe end up closer to each other.

What the Cafe Sent Back

Five things came out of that visit. The first one overturns the decision this whole case study is built on, which is the best argument I have for showing a thing to people instead of admiring it on your own bench.

  • The number should count up, not down. I had the big number showing grams remaining, falling to zero, because that takes the subtraction off you. Every barista there read it the other way round. They have spent thousands of pours watching a scale climb towards a target, and asking them to flip that habit costs more than the arithmetic it was saving. The app still does the sums — it should just show the half they already know how to read.
  • A cue before the stop, not only at it. Arriving at the target at full flow means going past it. A signal as you come into the last few grams makes you ease off, so the pour lands rather than slams. Sound does part of this today; doing it properly wants a buzz in your hand, which is one of the things a browser cannot reach on an iPhone.
  • Record a brew as you make it. Not everyone works from a recipe. Some pour by feel and only afterwards want to keep what they just did. That runs the whole flow backwards — the app watching instead of instructing — and it is how a signature brew actually gets written down rather than half-remembered.
  • The Hario Switch needs its own kind of step. A switch dripper steeps and then releases, so the hold is not a gap between pours — it is the brew. My recipe model assumes pour, wait, pour. It needs a step that means closed, and a pour that resumes when you open it again.
  • A log that can explain itself. Grind size, bean, dripper, grinder, filter, water temperature. Without them a logged brew can tell you a pour missed by four grams but never why, which makes it a receipt rather than something you can learn from.

The last one matters most for the test I still owe. Overshoot on its own is a thin number; overshoot next to the grind and the dripper is the start of knowing what actually moves it.

Asking Someone to Recommend You, Without Making It Weird

A referral programme on Manulife's Customer Website. Three different moments where it can be offered, one flow underneath, and a friend on the other end who has to feel invited rather than sold to.

Role
User Experience Architect
Company
Manulife · Dec 2025 – Present
Scope
3 entry points · 2 sides of the flow
Status
Shipped

Overview

Manulife's Customer Website is where policy owners in Singapore manage what they already have. The referral module adds something different: a way for a happy customer to introduce a friend, with a reward on both sides once that friend actually becomes a customer. I designed the module end to end — where it gets offered, what the referrer sees, what the friend lands on, and the rules that hold the whole thing together.

The Challenge

A referral is a favour you ask of someone. Ask at the wrong moment and it reads as a sales pitch dressed up as a thank-you; ask badly and the person on the receiving end feels sold to by their own friend. Both are easy to do and hard to undo.

There were three places the business wanted to offer it, and they are not the same situation at all:

  • After a tNPS survey. Someone has just told us they would recommend us. That is the warmest moment there is — and also the one where a reward offer can cheapen what they just said.
  • Inside the website. No trigger, no warm moment. Just an entry point that has to explain itself from cold to someone who came to pay a premium.
  • Around a Financial Needs Analysis. A consultant is already involved, so the referral is half a conversation and half a product — and the two must not contradict each other.

Underneath all three sits the harder half. A referral only works if the friend shows up, and in insurance that means handing a stranger's phone number to someone who sells for a living. Get the consent wrong and it is not just rude, it is a regulatory problem.

The Solution

One flow, three doors into it. The entry points differ in tone and timing; the machinery behind them — eligibility, consent, link generation, consultant assignment, reward — is the same in every case.

The referral is to a person, not a company. The referrer picks which financial consultant they are vouching for, and that choice carries all the way through to what their friend sees. And the friend's page leads with who sent them and what will actually happen next, before it asks for anything.

Three Ways In

I mapped each entry point as a service blueprint before designing a screen — referrer on one lane, the friend on another, and the system work underneath. It is the only way to see that three different front doors can share one set of rules, and the only way to spot where a reward is promised before anyone has checked it can be paid.

The blueprints did something else useful: they gave the business a thing to argue with. Stakeholders who will not read a spec will happily tell you a lane is wrong.

The Storyboard

A blueprint tells you what happens. It does not tell you what it feels like to be asked for a favour by your insurer, which is the part of this that could go wrong without a single lane being incorrect. So the same flow got told a second way — a cast of three, and the journey as scenes, each one tagged with whose turn it is. Each story runs left to right; drag it, or use the arrows.

Story 1 — after a good experience

  1. A good experience, first

    Randy finishes a transaction on the Customer Website and it goes well. Nothing about referral has happened yet — this is the thing a referral is made of, and the programme has no business existing before it.

  2. He scores it a ten

    The tNPS survey arrives when he logs out and he rates the experience a ten. That score is the trigger: the only people asked are the ones who have just said, unprompted, that they were happy.

  3. Fourteen days later, an invitation

    An email asks whether he would introduce family or friends to the consultant he dealt with. It arrives two weeks after the survey rather than in the same breath as it.

  4. He has someone in mind

    Randy thinks of Sarah, a friend who would get something out of talking to his consultant. He chooses Refer now and signs in to the Customer Website.

  5. Agree, generate, share

    He accepts the terms, generates a referral code tied to the consultant he picked, and sends it to Sarah on WhatsApp — the sharing happens where the friendship already is, not inside our product.

  6. Sarah sees who it came from

    The message arrives from someone she knows rather than from an insurer she has never dealt with. She opens the link, reads what it is, and fills in the form.

  7. The referral becomes a lead

    Her submission is validated and routed to the consultant Randy chose, who receives her details and arranges a conversation. The name Randy vouched for is the name Sarah was told about.

  8. A conversation, not a pitch

    Priya meets Sarah, works through what she needs and what she is saving towards, and recommends from there — then stays with her through the next steps.

  9. Both sides get paid

    Once the qualifying criteria are met during the FNA, the reward is issued to Randy and to Sarah. The friend is not the mechanism by which the referrer gets something.

Story 2 — from inside the app

The second and third stories are short for a reason. They differ only at the front door — a notification on a phone, or a consultant raising it across a desk. From the referral page onwards each one becomes the first story, which is the whole argument for building the rules once instead of three times.

  1. A push notification

    Randy sees the programme announced on his phone and opens MyManulife to find out what it is. The referral card sits on the home screen among his policies, so the offer arrives while he is already looking at what he holds with us.

Story 3 — raised in a policy conversation

  1. It comes up in conversation

    Randy is sitting with his consultant about a policy, and she introduces the programme as part of that conversation rather than as a separate pitch at the end of it.

  2. The terms, read out loud

    The consultant goes through the terms, the conditions and PDPA with him in person. Consent carries the same weight whether it is a checkbox or someone explaining it across a desk.

Design Process

1

Treat consent as the structure, not the small print

  • The page cannot produce a referral link until the referrer has actually agreed to the terms — the checkbox gates the action rather than sitting under it as decoration
  • The eligibility rules sit above that: the friend must be new to Manulife, the referrer must hold a policy, and both are stated before anyone invests effort
  • On the friend's side, a separate and specific consent — to be contacted by the named consultant, about this referral — rather than a blanket marketing opt-in
2

Make one page do two jobs

  • Before you agree, the page is an explanation and the button reads "Generate referral link"
  • After you agree, the same page becomes a sharing tool: the consultant card grows a referral code with a copy control, and the button becomes "Invite friends"
  • No second screen, no navigation — the state change is the confirmation that something happened
3

Keep the consultant attached to the referral

  • The referrer chooses the consultant they are willing to vouch for, from cards showing name and contact details rather than a dropdown of strings
  • That choice travels: the friend's page opens with "You will be connected with" and the same person
  • It turns an abstract lead into an introduction between two named people, which is what a referral actually is
4

Earn the friend's details before asking for them

  • The page opens with who referred them, by name, with a celebratory mark — the warmth comes from their friend, not from us
  • "What to expect" explains what a financial consultation involves in three lines, placed above the form rather than after it
  • The form asks for name, mobile and email, then lets them choose how they would rather be contacted — WhatsApp, phone or email — so the first approach arrives the way they picked
5

Tell the story before building the screens

  • Built an illustrated storyboard of the whole journey, each beat labelled with whose turn it is — customer, consultant, system
  • It gave stakeholders something they could follow without a walkthrough, and surfaced disagreements about the reward rules while they were still cheap to fix
  • The blueprint answers "what happens"; the storyboard answers "what does this feel like", and different rooms need different ones

What I Took From It

  • Consent is a structural decision. Treated as small print it is a checkbox under a button. Treated as structure it decides what the page can do and when — and the version that gates the action is both the compliant one and the clearer one.
  • A referral has two users and only one of them is your customer. The friend never agreed to anything, never heard of the programme, and owes you nothing. Designing their page first would have been the better order.
  • The warmest moment is the most fragile one. Immediately after someone says they would recommend you is when they are most likely to refer and most likely to feel used. The offer has to read as a way to act on what they just said, not as a reward for saying it.
  • Blueprints and storyboards are not the same tool. One answers what happens and where it can break; the other answers what this feels like and whose turn it is. Bringing the wrong one into a room costs you the meeting.
  • Sharing belongs outside the product. People refer friends in the places they already talk to them. Our job stopped at producing a link worth sending.

AIA Digital Design System

Building a comprehensive design system from scratch for a fast-growing insurance business

Role
UX Consultant
Duration
2 Years
Team
3 designers, 4 developers, 1 PM
Measured
~60% faster page build

Overview

When I joined AIA, they had grown from 5 to 50 designers in 18 months. Their product had evolved organically, resulting in inconsistent UI patterns, duplicated components, and a development process that was slowing down with each new feature. I was tasked with creating a comprehensive design system that would scale with the company's rapid growth.

The Challenge

The main challenge was creating a system that could adapt to different regions while being flexible enough to accommodate rapid feature development. We needed to establish design principles, create a token system, build the component library, and migrate existing products without disrupting ongoing development.

The Solution

I led the creation of a comprehensive design system built on atomic design principles. We established a robust token system, created extensive component documentation, and implemented a phased migration strategy that allowed teams to adopt the system gradually.

Design Process

1

Discovery & Audit

  • Conducted a comprehensive audit of existing UI patterns across all products, identifying 200+ unique variations of what should have been standard components.
  • Interviewed stakeholders from design, engineering, and product teams to understand pain points and requirements.
  • Analyzed competitor design systems and industry best practices to inform our approach.
2

Foundation & Principles

  • Established core design principles focused on clarity, efficiency, and scalability that would guide all design decisions.
  • Created a comprehensive token system covering colors, typography, spacing, and motion that could adapt to light and dark themes.
  • Defined component hierarchy and naming conventions that would scale with the system's growth.
3

Component Development

  • Built the library out from foundational elements — buttons, inputs, cards — into the compound patterns that pages are actually assembled from.
  • Each component included multiple variants, states, and comprehensive documentation with usage guidelines.
  • Collaborated closely with engineers to ensure components were built with accessibility, performance, and developer experience in mind.
4

Documentation & Testing

  • Created extensive documentation including design guidelines, component specs, and implementation examples.
  • Set up automated visual regression testing to catch breaking changes early in the development process.
  • Established governance processes for proposing, reviewing, and implementing changes to the system.

Inside the System

Every component ships as documentation rather than just a symbol — what it is for, how it behaves, and which platforms have it ready. Each page carries its own version and a resource row covering the Figma kit, React, Vue, AEM and React Native, so a designer and an engineer can check the same page and get the same answer.

Key Learnings
