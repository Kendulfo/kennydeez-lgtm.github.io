Segstream Design System

Rebuilding a design system so that everything themeable lives in variables — one token edit moves the entire product, with no manual cleanup.

Role
Lead UI/UX Designer
Version
v2.0, Sep 2026
Scale
40 sets · 485 variants
Impact
Retheme in 5 edits

Overview

Segstream's design system, rebuilt so that every colour, size, radius and typeface lives in a variable. Version 2.0 ships 40 component sets at 485 variants, 416 variables across seven collections, 23 text styles and a local 54-glyph icon set, with two colour modes and three density modes throughout. The organising promise is simple: one token edit moves the entire product — every component, every screen, both modes — with no manual cleanup afterwards.

The Challenge

The original file had 19 component sets and 245 variables, and it had drifted. Colour was bound directly to primitives in places, so a brand change meant hunting through components rather than editing a ramp. Dark mode existed in name only. There was no icon set, and the documentation was built from raw hex values that quietly disagreed with the components they described. Rethemeing was manual work with no way to know when it was finished.

The Solution

A three-tier token architecture, held together by one rule: a component never binds to a primitive. Raw hex lives in a hidden primitives collection. A semantic layer — background, foreground, border, brand, status, shadow — carries both modes and aliases those primitives. Component tokens alias the semantic and layout tiers in turn. On top of that structure, an entire retheme collapses to five edits: the brand ramp, an optional neutral ramp, two font families, three radius values, and a single logo component.

Design Process

1

Audit what was there

  • Catalogued the existing file: 19 component sets, 245 variables, and documentation generated from raw hex rather than from the tokens themselves
  • Traced where colour bound straight to primitives, which is what made rethemeing a manual hunt
  • Established that dark mode was present in name only, and that there was no icon set to speak of
2

Rebuild the token foundation

  • Seven variable collections arranged in three tiers, each with scopes and descriptions, and primitives hidden from publishing so they cannot be bound by accident
  • A semantic colour layer carrying genuine light and dark modes, verifiable side by side on the Colors page before a single screen is touched
  • Layout tokens with Compact, Default and Spacious density modes, and a typography collection with separate desktop and mobile scales
3

Rebuild the component library

  • 40 component sets at 485 variants, each page following the same shape so reading one teaches you how to navigate the rest
  • A shared property vocabulary — Variant, Type, State, Checked, Size, Mode — so the same word means the same thing on every component instead of being reinvented per family
  • A local 54-glyph icon set drawn on a 24px grid, with every fill bound to a token so an icon inside a button inherits that button's foreground colour
  • Building blocks prefixed with a dot to keep them out of the asset panel while still composing the larger components
4

Document it so it holds

  • Foundations pages render from live variables — the swatches on screen are the tokens, so documentation cannot drift from the system
  • Patterns and Templates built only from instances, demonstrating how components combine without introducing new one-off drawings
  • Every component page lints at zero across all eight checks, making "no raw values" an enforced property rather than a stated intention

Key Learnings

  • If something cannot be changed through a property, that is a gap in the component — not a reason to detach. Exposing every visible property is what keeps instances intact.
  • Composition beats redrawing. A modal footer holds real Button instances; redrawing a component inside another quietly breaks the token chain that everything else depends on.
  • An overridden font size survives happily until the scale changes, then silently disagrees with everything around it. Binding every text node to a style avoids a class of bug that is invisible until it is everywhere.
  • Density and breakpoint belong on the page frame, not on individual components. Setting them per component is how a system starts to contradict itself.
  • Documentation that renders from live tokens cannot drift. Documentation built from copied values always does.
  • State the limits in the open. Success, warning and error keep their own colour scales because Figma variables cannot compute colour — recolouring them means editing 33 more stops. Writing that down is better than letting the next person discover it halfway through a rebrand.

Linking an Insurance Policy Inside a Banking App

EastWest Bank customers hold EastWest Ageas policies they can only see by logging into a separate site. This flow brings those policies into the banking app — proving identity, capturing consent, and handling every way the link can fail.

Role
Product design — flows, states, UX writing
Platform
Mobile · EastWest Bank app
Partner
EastWest Ageas Life Insurance
Scope
9 flows · 80+ screens

Overview

Plenty of EastWest Bank customers also hold an EastWest Ageas life insurance policy — but the two lived apart. Checking a policy meant leaving the banking app, remembering a second set of credentials, and signing into an insurance site built for a different purpose. Most people simply never looked. This project brings those policies into the app customers already open daily, and designs the whole connection: who you say you are, what you agree to, and what happens when any part of it goes wrong.

The Challenge

Linking a bank account to an insurer is only partly a technical problem. It is mostly a trust problem. The flow has to prove identity convincingly enough to justify showing financial products, ask for consent in language a person can actually read, and never strand someone when a policy number is mistyped, a one-time code expires, or the insurer's system stops answering. The happy path is the short part of this work — the failures are where the experience is won or lost, and they are usually the part nobody draws.

The Solution

One clear journey — prompt, consent, policy number, one-time code, handoff — with every branch off it designed rather than left for the back end to explain. Friction is sized to consequence: linking moves quickly, unlinking stops to confirm. Failures are separated by cause, so a wrong code and an expired code say different things and offer different ways forward. Contact details are validated at the point of entry instead of failing silently later. And a customer who holds no policy meets a short introduction rather than a locked door.

Design Process

1

Map the journey end to end

  • Charted the happy path first — prompt, consent, policy number, one-time code, handoff — so the shape of the journey was settled before any state was styled
  • Numbered every step in flow order, with letters marking alternate routes branching off a step, so a reviewer can follow a path without guessing
  • Laid the work out in lanes that read left to right, each lane a phase, keeping an 80-screen flow legible on one board
2

Earn the link with identity and consent

  • Designed verification as a sequence a person can follow — account details, then a one-time code — rather than one intimidating form
  • Wrote consent in plain language, making it clear what is being connected and what the bank will be able to see
  • Sized friction to consequence: linking is quick, while unlinking pauses to confirm, because the cost of an accidental unlink falls on the customer
3

Design the failures, not just the success

  • Six edge-case sets covering one-time codes, policy numbers, contact details, account linking, and the back end itself refusing to answer
  • Separated failures by cause — a wrong code and an expired code are different problems and get different messages and different next steps
  • Replayed the entire journey against a failing API, which surfaces gaps the happy path hides
  • Gave every refusal a named reason and a route out, so no screen is a dead end
4

Turn a dead end into an introduction

  • Designed a lead-capture path for customers with no policy to link, so the flow still has somewhere to go
  • Kept it to what is genuinely needed to follow up, rather than a full application inside a banking app
  • Designed its failure states too — field rejections and submission failures — so the cross-sell path holds up as well as the primary one

Key Learnings

  • Friction should be proportional to consequence. Linking a policy can be quick; unlinking one should not be, because the person who pays for a mistaken tap is the customer.
  • Two different failures deserve two different messages. Collapsing "wrong code" and "expired code" into one generic error tells someone that something broke without telling them what to do about it.
  • Validating contact details at the point of entry prevents the worst kind of failure — the silent one, where a confirmation is sent somewhere the customer will never see it.
  • A refusal without a route out is a dead end. Naming the reason and offering the next step turns a stopped journey into a recoverable one.
  • Replaying the whole journey against a failing back end is the fastest way to find the states nobody designed.
  • Annotating a large flow in the file itself — numbered steps, lettered branches, lanes for phases — means engineering can read a path without a meeting to explain it.

Designing a Delivery App from Research to Launch

myEntrego is a customer-facing parcel app — book a delivery, pay for it, and see where it is. I owned it end to end, from user research through to the 113 screens that shipped on the App Store and Google Play.

Role
Lead UI/UX Designer — end to end
Platform
iOS & Android
Scope
113 screens · 2 personas
Outcome
4.8★, shipped to both stores

Overview

Entrego is a Philippine logistics company, and myEntrego is how its customers actually reach it — booking a delivery, paying for it, and tracking where the parcel has got to. This was mine from the first interview to the last screen: research and personas, a journey map, the information architecture, the booking flow, and 113 designed screens. It shipped to both app stores and settled at around 4.8 stars, with parcel tracking pulling the most repeat traffic.

The Challenge

Sending a parcel through a logistics provider meant phone calls, guesswork about cost, and no way to know where anything was once it left your hands. The research made the friction specific rather than general: booking took too many steps, addresses were hard to pin down, and the bill could not be read in full. The app also had to make sense to two very different people — a seller running a small business from her phone, and a courier who had spent ten years on a motorcycle and described himself as afraid of technology.

The Solution

Every significant decision traces back to something a real user said. Booking became a guided flow with saved addresses, so the second delivery is far quicker than the first. A shipping fee calculator puts the cost up front, before anyone commits. And tracking was made available without logging in at all — the thing people do most often became the thing that asks least of them, which is what turned it into the app's most returned-to screen.

Design Process

1

Research actual users, not assumed ones

  • Built two personas from gathered data rather than invention — Rica, a freelancer growing an online selling business, and Roger, a courier ten years into the job
  • Recorded frustrations in the users' own terms: a tedious booking process, trouble locating an address, and a bill that could not be seen in full
  • Kept a self-described "tech phobic but willing to learn" user in scope, which set the standard for how much each screen had to explain itself
2

Map the journey, including how it feels

  • Plotted the end-to-end journey in swimlanes — steps, actions, expectations, thoughts — and ran a feelings lane alongside them
  • Marked where people were confused or frustrated, and treated those low points as the brief rather than as commentary
  • Turned the "potential improvements" lane into the backlog the screens were designed against
3

Settle the structure before the pixels

  • Built a sitemap covering profile, saved addresses, bank accounts, the fee calculator, serviceable-area checking, pouch requests, FAQs and legal
  • Drew booking as a decision tree with explicit yes/no branches, including how saved addresses short-circuit the long path
  • Resolved the awkward questions on the flow board, where changing your mind costs nothing
4

Design it, then ship it

  • 113 screens from first-run onboarding through to payment confirmation
  • Standard delivery, drop-off, scheduling, remittances, tracking and modal states all specified rather than left implied
  • Shipped to the App Store and Google Play, where it has held around 4.8 stars

Key Learnings

  • Personas built from gathered data change what gets built; invented ones just decorate a deck. Rica's three frustrations became three features — saved addresses, a fee calculator, and readable billing.

  • Showing cost before commitment removes the most common reason a booking is abandoned halfway.
  • Owning the work from research through to launch means nothing is lost in translation between what a user said and what finally shipped.

Selling Health Cover Inside a Wallet App

KwikCare plans bought without ever leaving GCash — five tiers priced from ₱995 a month, a guided four-step purchase with health declaration and document upload, and a policy dashboard for every plan.

Role
Lead Product Designer
Platform
Mobile · GCash
Underwriter
PhilCare
Scope
5 plan tiers · 4-step purchase

Overview

KwikCare is health cover sold as a monthly subscription, underwritten by PhilCare and bought inside GCash — the wallet a large share of the Philippines already has open. The work covers the whole commercial path: comparing five plan tiers, understanding what each actually covers, completing a health declaration and document upload, paying from a wallet balance, and then living with the policy afterwards.

The Challenge

Insurance is difficult to sell on a phone for two reasons. The product is hard to compare — benefit limits, exclusions and waiting periods do not fit on a card — and the purchase asks for exactly the things people abandon forms over: identity documents, proof of income, and a declaration about their own health. Doing this inside someone else's app raises the bar again: the flow has to feel like a native part of GCash, or the trust that made the wallet worth using does not carry across to the insurance sitting inside it.

The Solution

Tiers are presented as a comparison rather than a brochure: each plan leads with its price and its maximum benefit limit, then lists what it actually includes. Every tier carries its own covered-and-excluded breakdown instead of one generic table, because the differences between plans are the entire decision. The purchase is cut into four named steps so the length is visible from the start, and the health declaration is kept short and in-flow rather than deferred to a form nobody finishes.

Design Process

1

Wireframe the whole purchase before styling any of it

  • Laid out the full path — plan selection, policy holder details, documents, review, payment handoff — in low fidelity first
  • Settled the step count early, which is what determines whether the purchase feels finishable
  • Used the wireframes to expose the awkward middle of the flow, where identity and health questions land
2

Make five tiers genuinely comparable

  • Led every plan card with price and maximum benefit limit, the two numbers the decision actually turns on
  • Gave each tier its own covered, excluded and expanded-detail views rather than one shared table that hides the differences
  • Marked the popular tier explicitly, so the default choice is obvious to someone who does not want to become an expert
3

Design the parts people abandon

  • Split the purchase into four named steps — insurer details, policy holder information, document upload, review — so progress is always legible
  • Designed the health declaration as a short in-flow set of statements, with a popup for the detail rather than a wall of text inline
  • Specified document upload states properly: accepted formats, size limits, in-progress and attached, because this is where a purchase quietly dies
  • Ended on an explicit review of everything captured before any money moves
4

Iterate, then specify it for build

  • Worked through four versions, keeping the superseded ones archived rather than deleted so the reasoning stays visible
  • Built a prototype of the working design so the flow could be walked rather than described
  • Produced a specifications page for handoff, alongside FAQ, how-to-claim and contact screens that the product needs after the sale

Key Learnings

  • Selling inside someone else's app means inheriting their trust. The flow has to feel continuous with the wallet, or the credibility does not transfer to the product sitting in it.

AIA Digital Design System

Building a comprehensive design system from scratch for a fast-growing insurance business

Role
UX Consultant
Duration
2 Years
Team
3 designers, 4 developers, 1 PM
Reach
18 markets · 5 platforms

Overview

When I joined AIA, they had grown from 5 to 50 designers in 18 months. Their product had evolved organically, resulting in inconsistent UI patterns, duplicated components, and a development process that was slowing down with each new feature. I was tasked with creating a comprehensive design system that would scale with the company's rapid growth.

The Challenge

The main challenge was creating a system that could adapt to different regions while being flexible enough to accommodate rapid feature development. We needed to establish design principles, create a token system, build the component library, and migrate existing products without disrupting ongoing development.

The Solution

I led the creation of a comprehensive design system built on atomic design principles. We established a robust token system, created extensive component documentation, and implemented a phased migration strategy that allowed teams to adopt the system gradually.

Design Process

1

Discovery & Audit

  • Conducted a comprehensive audit of existing UI patterns across all products, identifying 200+ unique variations of what should have been standard components.
  • Interviewed stakeholders from design, engineering, and product teams to understand pain points and requirements.
  • Analyzed competitor design systems and industry best practices to inform our approach.
2

Foundation & Principles

  • Established core design principles focused on clarity, efficiency, and scalability that would guide all design decisions.
  • Created a comprehensive token system covering colors, typography, spacing, and motion that could adapt to light and dark themes.
  • Defined component hierarchy and naming conventions that would scale with the system's growth.
3

Component Development

  • Built the library out from foundational elements — buttons, inputs, cards — into the compound patterns that pages are actually assembled from.
  • Each component included multiple variants, states, and comprehensive documentation with usage guidelines.
  • Collaborated closely with engineers to ensure components were built with accessibility, performance, and developer experience in mind.
4

Documentation & Testing

  • Created extensive documentation including design guidelines, component specs, and implementation examples.
  • Set up automated visual regression testing to catch breaking changes early in the development process.
  • Established governance processes for proposing, reviewing, and implementing changes to the system.

Inside the System

Every component ships as documentation rather than just a symbol — what it is for, how it behaves, and which platforms have it ready. Each page carries its own version and a resource row covering the Figma kit, React, Vue, AEM and React Native, so a designer and an engineer can check the same page and get the same answer.

Key Learnings

  • Early collaboration with engineering teams is crucial for creating components that are both design-forward and developer-friendly.
  • Incremental adoption works better than big-bang migrations — teams can adopt the system at their own pace while seeing immediate benefits.
  • Documentation is just as important as the components themselves — clear guidelines prevent misuse and ensure consistency.
  • Building a governance process early helps maintain system quality as it scales and more contributors join.
  • Regular audit cycles help identify gaps and opportunities for improvement as the product evolves.
  • Token systems provide flexibility for theming and ensure visual consistency across all components and products.
